Decisions
- Docker Postgres Container: Local Postgres runs via Docker Compose (postgres:16) instead of a native install, for deployment parity and easy reproducibility. Credentials in .env (gitignored), not hardcoded in compose. pgAdmin connects to it as GUI client.
- Mapping extensions: Vehicle -> VehicleDto mapping lives in a dedicated Vehicles/Mappings/MappingExtensions.cs (extension method vehicle.ToModel()) rather than a static factory on the DTO itself. Intentional from the start to scale cleanly as more entities/mappings get added later.
- Repository placement: IVehicleRepository interface lives in Application, concrete EF Core implementation lives in Infrastructure. Dependencies point inward (Infrastructure -> Application -> Domain), so Application never depends on Infrastructure.
- Mapping extensions location: lives in Application, not Domain, because VehicleDto is an Application concern (the shape exposed outward). Domain is the innermost layer and can't reference Application, so mapping code touching both types has to sit in Application.
- DB connection string: stored via .NET User Secrets (dotnet user-secrets) rather than appsettings.Development.json, so the real Postgres credentials never get committed to git — same reasoning as .env being gitignored for Docker.
- Vehicle type: Bruno is a general vehicle hire business, not just cars — added a VehicleType enum on Vehicle rather than modelling per-type inheritance. Business reason: all vehicle types share the same fields for this system's purposes, so a discriminator enum is simpler than a type hierarchy and still lets the fleet expand to new vehicle types by just adding an enum value. Widened to cover non-road vehicles too: Car, Suv, Van, Truck, Bus, Minibus, Motorcycle, Trailer, Tractor, Helicopter, Boat, Other.
- Removed Mileage and ServiceHistory from Vehicle: follow-up from the VehicleType change - both were car/road-vehicle-specific assumptions (odometer km, dealership-franchise servicing) that don't generalize to a helicopter or tractor, and neither is in the spec's required fields, so they were dropped rather than reworked.
- Validation error shape: ExceptionHandlingMiddleware now returns FluentValidation failures as a field-keyed errors dictionary (ValidationProblemDetails, RFC 7807 - {"errors": {"PricePerDay": ["..."]}}) instead of a flat list of message strings. Matches ASP.NET Core's own built-in model-binding error shape, so the frontend has one consistent error format and can map errors[fieldName] straight to the matching input for inline validation display.
- API key security: header-based (X-Api-Key) via ApiKeyMiddleware, checked against a key stored in User Secrets (same reasoning as the DB connection string - never hardcoded/committed). /swagger paths are excluded from the check so the docs UI itself stays browsable; actual endpoint calls (including from Swagger's "Try it out") still need the key. Swagger's Authorize button is wired up via a security definition so the key only needs to be entered once per session in the UI.
- Frontend framework: Next.js instead of the spec's literally-named React stack (Vite/CRA + React Router). Deliberate deviation, not an oversight - reasoning: Kyle's existing familiarity with Next.js/Vercel, easy Vercel deployment for this project's planned deploy step, built-in file-based routing (app/ folder structure maps directly to routes, no manual router config), and SSR/React Server Components available if useful later. Still React underneath, still TypeScript - the deviation is specifically from "Vite or CRA" + "React Router" being named explicitly in the spec's Required Stack for React.
- Package manager: pnpm instead of npm for the frontend. Reasoning: pnpm is more performant than npm - it uses a single global content-addressable store and hard-links packages into node_modules instead of copying them per-project, so installs are faster and use far less disk space, especially valuable as more packages (like shadcn/ui components) get added.
- Styling: Tailwind CSS, scaffolded in directly via create-next-app's --tailwind flag. Reasoning: Kyle's existing experience with it and convenience, not a spec requirement either way (spec doesn't name a styling approach). Also sets up for shadcn/ui later (a component library built on Tailwind) - planning to use it for the same reason as picking any component library: no point hand-building buttons/inputs/dialogs/etc from scratch when a well-built, working set already exists with little to no friction to adopt. Satisfies the spec's "basic reusable components" expectation for free rather than reinventing it.
- NotFoundException: added a plain Application-layer exception, caught in ExceptionHandlingMiddleware alongside ValidationException and mapped to 404 (ProblemDetails). Used by GetVehicleByRegistrationNumber and UpdateVehicle when the vehicle doesn't exist, instead of each handler/controller inventing its own null-check-and-return-404 pattern. Same "throw deep, catch once at the edge" approach as the validation error handling.
- Update endpoint doesn't touch ImageUrls: UpdateVehicleCommand omits ImageUrls entirely; Vehicle.Update() already defaults imageUrls to null -> keeps existing list unchanged. Deliberate scope cut for now, not an oversight - image management on update can come later.
- Update route/body id binding: PUT /api/vehicles/{id} takes Guid id from the route plus UpdateVehicleCommand from the body (which doesn't need to include Id at all), then the controller does `command with { Id = id }` before sending - keeps the route as the source of truth for which resource is being updated rather than trusting a body-supplied id.
- Image upload flow: upload fires the moment a file is selected (not chained into vehicle creation on submit). Two independent actions - upload returns a URL immediately, "Add Vehicle" submit is a separate action that just sends whatever URLs already exist. Reasoning: better UX (upload failures surface immediately, not after filling the whole form), and it mirrors how the backend is already split (ImagesController and VehiclesController are unrelated endpoints; CreateVehicleCommand only ever knows about plain URL strings, never blob storage). Chaining upload->create on submit would couple two independent operations together and doesn't even remove the minor orphaned-blob risk (upload could still succeed while create fails) - it just moves the same risk later with worse UX.
- Azure Blob Storage credentials: reusing an existing POC storage account ("blobpocnexusdev"), new container "kylebruno" made for this project with anonymous read access at Blob level (not Container level - we only ever access known URLs, never need to enumerate the container, so Blob level is the better fit, not just "good enough"). Connection string + container name stored in User Secrets, same reasoning as everything else - anonymous access only covers reads, uploading always needs the connection string regardless of the container's public access setting.

Secrets / Environment Variables (what's needed if/when this gets deployed)
- ConnectionStrings:DefaultConnection - Postgres connection string. Local: User Secrets, pointing at the Docker container. Deploy: needs to point at whatever Postgres instance is hosted for production (a managed cloud Postgres, not the local Docker container) - set via the hosting platform's env vars/app settings, not committed.
- ApiKey - the header-based API key value. Local: User Secrets. Deploy: needs an equivalent secret/env var configured on the hosting platform (e.g. Azure App Service Configuration, or a secrets manager) - should probably be a different, stronger value than the local dev key.
- AzureBlobStorage:ConnectionString - Azure Storage account connection string (write access for uploads). Local: User Secrets. Deploy: same key needs to exist as a platform secret/env var; the underlying storage account itself doesn't need to change, since this container can be reused as-is.
- AzureBlobStorage:ContainerName - "kylebruno". Not sensitive on its own (just a name), but kept alongside the connection string in User Secrets for consistency. Deploy: same value, just needs to be present as config wherever it's hosted.
- Docker .env (POSTGRES_DB/USER/PASSWORD) - local-only concern for running Postgres in a container on this machine. Not relevant at deploy time since production would use a real hosted Postgres instance instead of this Docker setup.

Questions
Q: What's the dependency direction across the layers?
A: Domain depends on nothing. Application depends on Domain only. Infrastructure depends on Application (+ Domain transitively). Api depends on both Infrastructure and Application. So Domain <- Application <- Infrastructure <- Api - dependencies always point inward, toward Domain.

Q: What do Up() and Down() mean in an EF Core migration?
A: Up() applies the migration - the schema changes to move the DB forward (e.g. CreateTable). Down() reverses it - what to run to undo this migration and get back to the previous schema state (e.g. DropTable). Down() is what runs if you ever roll back a migration.

Q: The validation failure is thrown inside the MediatR pipeline behavior, not the controller - how does that error actually reach the frontend as a response?
A: Nothing in between catches it - the ValidationException just propagates up through every awaited caller (pipeline behavior -> MediatR.Send -> controller action -> MVC internals) until it hits ExceptionHandlingMiddleware, which wraps the entire rest of the pipeline in a try/catch (it's registered before MapControllers, so its "await _next(context)" covers routing + controller + MediatR + handler, all of it). That catch block is what actually sets the 400 status and writes the ValidationProblemDetails JSON to the real HTTP response. So the frontend just gets a normal HTTP 400 + JSON body like any other error - nothing special on its end.

Q: What is Swashbuckle?
A: .NET library that auto-generates OpenAPI/Swagger docs from controllers/DTOs and serves the Swagger UI page. Satisfies the spec's "Swagger documentation enabled" requirement.

Q: How does VehicleRepository know it's talking to Postgres instead of Mongo etc, and how does it get the DbContext - is that passed in by the handler?
A: VehicleRepository itself doesn't know it's Postgres - it only knows ApplicationDbContext, and EF Core's LINQ API (_dbContext.Vehicles.FirstOrDefaultAsync(...) etc) is provider-agnostic. The one place Postgres gets chosen is Program.cs: builder.Services.AddDbContext<ApplicationDbContext>(options => options.UseNpgsql(...)) - that .UseNpgsql(...) line is the single point in the whole solution that says "this DbContext talks to Postgres." If swapping to a different relational DB (e.g. SQL Server), that's the only line that would need to change (Mongo is a bigger swap since it isn't relational and EF Core doesn't support it the same way).

On how the DbContext gets into the repository - not through the handler, and nothing is passed manually anywhere. It's constructor injection via .NET's built-in DI container:
1. Program.cs registers two things: ApplicationDbContext (via AddDbContext) and IVehicleRepository -> VehicleRepository (via AddScoped).
2. When a request comes in, MediatR asks the DI container for a CreateVehicleCommandHandler. Its constructor needs an IVehicleRepository - the container sees that's registered to resolve to VehicleRepository.
3. To build a VehicleRepository, the container looks at its constructor, sees it needs an ApplicationDbContext, and supplies one automatically - because that's also registered.
4. So: Api (DI container assembles everything) -> Handler only ever sees IVehicleRepository -> VehicleRepository only ever sees ApplicationDbContext -> ApplicationDbContext is the only thing that knows about Npgsql/Postgres.

Nobody manually passes ApplicationDbContext anywhere - the container wires the whole chain based purely on constructor parameter types and what's registered in Program.cs. This is also why the handler can be unit tested by just mocking IVehicleRepository - it never needs a real database at all.

Technical Details

Azure Blob Storage (vehicle images)
- Reusing an existing Azure resource from a prior POC rather than provisioning new: Storage account "blobpocnexusdev", new blob container "kylebruno" created specifically for this project, container anonymous access level set to "Blob" (anonymous read access to individual blobs by URL, not container listing).
- Because the container allows anonymous blob-level read, no SAS token or auth is needed for retrieval - once a file is uploaded, its blob URL is directly publicly viewable. This is what satisfies "image retrieval from url" simply: the DB just needs to store the URL, no dedicated retrieval endpoint required.
- Upload still goes through the backend (not client-direct-to-blob) so the backend controls what gets stored and appends the resulting URL to Vehicle.ImageUrls.

EF Core persistence setup
- Infrastructure/Persistence/ApplicationDbContext.cs — DbSet<Vehicle>, applies entity configs from the assembly (ApplyConfigurationsFromAssembly) so new entity configs get picked up automatically without editing OnModelCreating each time.
- Infrastructure/Persistence/Configurations/VehicleConfiguration.cs (IEntityTypeConfiguration<Vehicle>) — table name "Vehicles", unique index on RegistrationNumber, max lengths on string fields (RegistrationNumber 20, Make/Model 50, SellerName 100), PricePerDay mapped as numeric(10,2) (never float/double for money), Colour/ServiceHistory enums stored as int.
- Soft delete enforced via a global query filter on the entity config (HasQueryFilter(v => !v.IsDeleted), in VehicleConfiguration.Configure) rather than each handler/query remembering to filter it out — every query against Vehicles automatically excludes soft-deleted rows at the EF Core level, applied by EF itself as a silent WHERE clause on every LINQ query against DbSet<Vehicle>. Confirmed in practice: GetByIdAsync/GetByRegistrationNumberAsync/GetPagedAsync all just write plain queries with zero IsDeleted-awareness and still exclude soft-deleted rows correctly - including SoftDeleteVehicle's own repeat-delete case (can't fetch an already-deleted vehicle to delete it again, so it 404s).
- Program.cs registers ApplicationDbContext via AddDbContext with UseNpgsql, reading the connection string from configuration (ConnectionStrings:DefaultConnection) — supplied via .NET User Secrets locally (see commands below), never hardcoded or committed.

Code-first migrations — flow
- Code-first means the C# entity + EF Core config is the source of truth for the schema, not a hand-written SQL script. Flow: 1) define/change Vehicle entity (Domain) 2) configure it via VehicleConfiguration (Infrastructure) 3) run "dotnet ef migrations add <Name>" - EF diffs the model against the last snapshot and generates a migration file with Up()/Down() 4) run "dotnet ef database update" - applies pending migrations to the actual DB.
- Requires Microsoft.EntityFrameworkCore.Design in both the project holding the DbContext (Infrastructure) and the startup project (Api) - the CLI tools need it in the startup project to build/run the app's DI container.
- Each migration produces 3 files: <timestamp>_<Name>.cs (the actual Up/Down), <timestamp>_<Name>.Designer.cs (tooling metadata), and ApplicationDbContextModelSnapshot.cs (single file, current full model state, updated every migration so EF can diff future changes against it). All 3 get committed to git.
- First migration: InitialCreate - creates the Vehicles table matching VehicleConfiguration (unique index on RegistrationNumber, numeric(10,2) PricePerDay, enums as int, etc.).

CORS
- Added a named CORS policy allowing http://localhost:3000 (Next.js dev server default port), AllowAnyHeader + AllowAnyMethod, registered via AddCors/UseCors in Program.cs.
- Ordering matters: UseCors is placed BEFORE ApiKeyMiddleware in the pipeline. Browser CORS preflight (OPTIONS) requests never include custom headers like X-Api-Key, so if ApiKeyMiddleware ran first it would reject every preflight with 401 and break CORS entirely. ASP.NET's CORS middleware short-circuits matching preflight requests itself (responds directly, never calls next), so placing it first means preflights never reach the API key check at all.

Swagger wiring
- Replaced the template's built-in AddOpenApi()/MapOpenApi() (just a raw OpenAPI JSON document, no browsable UI) with Swashbuckle: AddEndpointsApiExplorer() + AddSwaggerGen() in services, UseSwagger() + UseSwaggerUI() in the dev-only pipeline block. This is what actually gives a visual Swagger page at /swagger, satisfying the spec's "Swagger documentation enabled" requirement.
- Wiring Program.cs alone isn't enough to actually see the UI when running from Visual Studio - Properties/launchSettings.json also needs "launchBrowser": true and "launchUrl": "swagger" on each profile (http/https), otherwise the app runs fine but no browser opens (or it opens to a blank/404 root page with no launchUrl set).
