Decisions
- Docker Postgres Container: Local Postgres runs via Docker Compose (postgres:16) instead of a native install, for deployment parity and easy reproducibility. Credentials in .env (gitignored), not hardcoded in compose. pgAdmin connects to it as GUI client.
- Mapping extensions: Vehicle -> VehicleDto mapping lives in a dedicated Vehicles/Mappings/MappingExtensions.cs (extension method vehicle.ToModel()) rather than a static factory on the DTO itself. Intentional from the start to scale cleanly as more entities/mappings get added later.
- Repository placement: IVehicleRepository interface lives in Application, concrete EF Core implementation lives in Infrastructure. Dependencies point inward (Infrastructure -> Application -> Domain), so Application never depends on Infrastructure.
- Mapping extensions location: lives in Application, not Domain, because VehicleDto is an Application concern (the shape exposed outward). Domain is the innermost layer and can't reference Application, so mapping code touching both types has to sit in Application.
- DB connection string: stored via .NET User Secrets (dotnet user-secrets) rather than appsettings.Development.json, so the real Postgres credentials never get committed to git — same reasoning as .env being gitignored for Docker.
- Vehicle type: Bruno is a general vehicle hire business, not just cars — added a VehicleType enum on Vehicle rather than modelling per-type inheritance. Business reason: all vehicle types share the same fields for this system's purposes, so a discriminator enum is simpler than a type hierarchy and still lets the fleet expand to new vehicle types by just adding an enum value. Widened to cover non-road vehicles too: Car, Suv, Van, Truck, Bus, Minibus, Motorcycle, Trailer, Tractor, Helicopter, Boat, Other.
- Removed Mileage and ServiceHistory from Vehicle: follow-up from the VehicleType change - both were car/road-vehicle-specific assumptions (odometer km, dealership-franchise servicing) that don't generalize to a helicopter or tractor, and neither is in the spec's required fields, so they were dropped rather than reworked.

Questions
Q: What's the dependency direction across the layers?
A: Domain depends on nothing. Application depends on Domain only. Infrastructure depends on Application (+ Domain transitively). Api depends on both Infrastructure and Application. So Domain <- Application <- Infrastructure <- Api - dependencies always point inward, toward Domain.

Q: What do Up() and Down() mean in an EF Core migration?
A: Up() applies the migration - the schema changes to move the DB forward (e.g. CreateTable). Down() reverses it - what to run to undo this migration and get back to the previous schema state (e.g. DropTable). Down() is what runs if you ever roll back a migration.

Q: What is Swashbuckle?
A: .NET library that auto-generates OpenAPI/Swagger docs from controllers/DTOs and serves the Swagger UI page. Satisfies the spec's "Swagger documentation enabled" requirement.

Q: How does VehicleRepository know it's talking to Postgres instead of Mongo etc, and how does it get the DbContext - is that passed in by the handler?
A: VehicleRepository itself doesn't know it's Postgres - it only knows ApplicationDbContext, and EF Core's LINQ API (_dbContext.Vehicles.FirstOrDefaultAsync(...) etc) is provider-agnostic. The one place Postgres gets chosen is Program.cs: builder.Services.AddDbContext<ApplicationDbContext>(options => options.UseNpgsql(...)) - that .UseNpgsql(...) line is the single point in the whole solution that says "this DbContext talks to Postgres." If swapping to a different relational DB (e.g. SQL Server), that's the only line that would need to change (Mongo is a bigger swap since it isn't relational and EF Core doesn't support it the same way).

On how the DbContext gets into the repository - not through the handler, and nothing is passed manually anywhere. It's constructor injection via .NET's built-in DI container:
1. Program.cs registers two things: ApplicationDbContext (via AddDbContext) and IVehicleRepository -> VehicleRepository (via AddScoped).
2. When a request comes in, MediatR asks the DI container for a CreateVehicleCommandHandler. Its constructor needs an IVehicleRepository - the container sees that's registered to resolve to VehicleRepository.
3. To build a VehicleRepository, the container looks at its constructor, sees it needs an ApplicationDbContext, and supplies one automatically - because that's also registered.
4. So: Api (DI container assembles everything) -> Handler only ever sees IVehicleRepository -> VehicleRepository only ever sees ApplicationDbContext -> ApplicationDbContext is the only thing that knows about Npgsql/Postgres.

Nobody manually passes ApplicationDbContext anywhere - the container wires the whole chain based purely on constructor parameter types and what's registered in Program.cs. This is also why the handler can be unit tested by just mocking IVehicleRepository - it never needs a real database at all.

Technical Details

EF Core persistence setup
- Infrastructure/Persistence/ApplicationDbContext.cs — DbSet<Vehicle>, applies entity configs from the assembly (ApplyConfigurationsFromAssembly) so new entity configs get picked up automatically without editing OnModelCreating each time.
- Infrastructure/Persistence/Configurations/VehicleConfiguration.cs (IEntityTypeConfiguration<Vehicle>) — table name "Vehicles", unique index on RegistrationNumber, max lengths on string fields (RegistrationNumber 20, Make/Model 50, SellerName 100), PricePerDay mapped as numeric(10,2) (never float/double for money), Colour/ServiceHistory enums stored as int.
- Soft delete enforced via a global query filter on the entity config (HasQueryFilter(v => !v.IsDeleted)) rather than each handler/query remembering to filter it out — every query against Vehicles automatically excludes soft-deleted rows at the EF Core level.
- Program.cs registers ApplicationDbContext via AddDbContext with UseNpgsql, reading the connection string from configuration (ConnectionStrings:DefaultConnection) — supplied via .NET User Secrets locally (see commands below), never hardcoded or committed.

Code-first migrations — flow
- Code-first means the C# entity + EF Core config is the source of truth for the schema, not a hand-written SQL script. Flow: 1) define/change Vehicle entity (Domain) 2) configure it via VehicleConfiguration (Infrastructure) 3) run "dotnet ef migrations add <Name>" - EF diffs the model against the last snapshot and generates a migration file with Up()/Down() 4) run "dotnet ef database update" - applies pending migrations to the actual DB.
- Requires Microsoft.EntityFrameworkCore.Design in both the project holding the DbContext (Infrastructure) and the startup project (Api) - the CLI tools need it in the startup project to build/run the app's DI container.
- Each migration produces 3 files: <timestamp>_<Name>.cs (the actual Up/Down), <timestamp>_<Name>.Designer.cs (tooling metadata), and ApplicationDbContextModelSnapshot.cs (single file, current full model state, updated every migration so EF can diff future changes against it). All 3 get committed to git.
- First migration: InitialCreate - creates the Vehicles table matching VehicleConfiguration (unique index on RegistrationNumber, numeric(10,2) PricePerDay, enums as int, etc.).
