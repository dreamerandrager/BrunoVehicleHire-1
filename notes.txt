Decisions
- Swagger UI intentionally hidden in production: registered only inside `if (app.Environment.IsDevelopment())` in Program.cs, so it's available locally but not on the deployed Azure App Service (which defaults to ASPNETCORE_ENVIRONMENT=Production). Not an oversight - no need to expose API docs publicly on a deployed instance protected by an API key.
- Backend + DB deployed manually to Azure, no CI/CD: DB is Azure Database for PostgreSQL Flexible Server (Burstable B1ms), API is Azure App Service (Linux, F1). Deployment is via Visual Studio's built-in Publish (right-click project -> Publish -> existing App Service) rather than GitHub Actions - Azure's Deployment Center CI/CD setup tried to auto-provision an Entra ID app registration + push OIDC secrets to GitHub and failed on both sides (no permission to create the app registration, no permission to write repo secrets). Given this only needs occasional manual redeploys for an assessment project, VS Publish was simpler and avoided debugging that permissions chain. Migrations applied manually too, via `dotnet ef database update` pointed at the Azure connection string. DB firewall is allow-all-IPs (0.0.0.0-255.255.255.255) and App Service has SCM Basic Auth Publishing Credentials enabled - both are deliberate time-saving trade-offs, not defaults.
- Frontend deployed on Vercel: chosen because it directly supports easy, free Next.js deployment with customizable domains - no config needed beyond Root Directory + env vars. Repo ended up migrated from the original GitHub account to Kyle's separate personal GitHub account mid-deploy: the original account was work-SSO-linked, which caused the Vercel project to get auto-scoped under the employer's ("agilebridges") Vercel team, and that team had Deployment Protection (Vercel Authentication) enabled org-wide - blocking public access to every deployment (even "Ready" ones with a fully correct build) with what looked like a 404. Re-imported cleanly under the personal GitHub + Vercel account once migrated, resolving it.
- SellerName renamed to OwnerName: "Seller" is sales-transaction terminology and made no sense for a hire business (Bruno Vehicle Hire) - nobody's selling anything, vehicles are hired out. Renamed across the full stack: Domain entity/EF config, Create/Update commands+handlers+validators, DTO, mapping, migration (RenameSellerNameToOwnerName - EF detected it as a true column rename, not drop+add, so no data loss), and every frontend type/schema/form/view referencing it.
- Dropped HireStartDate/HireEndDate, added Condition (0-4 enum: Poor, Fair, Good, VeryGood, Excellent) via migration - felt like hire dates would be more properties of a booking which arguably could be its own entity - whereas a condition is fully a property of the vehicle itself. 
- shadcn Select dropdown showed the raw index (e.g. "0") instead of the label after selecting: Base UI's Select.Value has no built-in mapping from a value to display text unless given either an `items` prop on Select.Root or a children render function - we were rendering bare `<SelectValue />` with neither. Fixed by passing `{(value) => options[Number(value)]}` as SelectValue's children in SelectFormField.
- Reversed the "Update doesn't touch ImageUrls" scope cut from earlier: Edit now supports replacing the vehicle's image (hover-to-change on the image in the edit modal), so UpdateVehicleCommand has ImageUrls back (Vehicle.Update() already accepted it optionally, so no Domain change needed). Since we only ever use imageUrls[0], "change image" just uploads a new image and replaces the single-element array - no multi-image management added.
- Edit UI restructured to match View: both now show the image on top (aspect-4/3, capped width, closer to square than the old full-width h-64 banner) with a 2-column layout below it (detail rows in View, form fields in EditVehicleForm) - the side-by-side View+Form arrangement from before is gone, replaced by EditVehicleForm owning its own image display (with the hover "Change Image" overlay) so the two modals look consistent.
- Condition badge colour mapping (constants/vehicle-condition-styles.ts): chose red->orange->blue->purple->green for Poor->Excellent (worst to best), reusing the palette suggested but reordered to read semantically (red=worst, green=best) rather than the literal order given - flagged for Kyle to confirm/adjust.
- Docker Postgres Container: Local Postgres runs via Docker Compose (postgres:16) instead of a native install, for deployment parity and easy reproducibility. Credentials in .env (gitignored), not hardcoded in compose. pgAdmin connects to it as GUI client.
- Mapping extensions: Vehicle -> VehicleDto mapping lives in a dedicated Vehicles/Mappings/MappingExtensions.cs (extension method vehicle.ToModel()) rather than a static factory on the DTO itself. Intentional from the start to scale cleanly as more entities/mappings get added later.
- Repository placement: IVehicleRepository interface lives in Application, concrete EF Core implementation lives in Infrastructure. Dependencies point inward (Infrastructure -> Application -> Domain), so Application never depends on Infrastructure.
- Mapping extensions location: lives in Application, not Domain, because VehicleDto is an Application concern (the shape exposed outward). Domain is the innermost layer and can't reference Application, so mapping code touching both types has to sit in Application.
- DB connection string: stored via .NET User Secrets (dotnet user-secrets) rather than appsettings.Development.json, so the real Postgres credentials never get committed to git — same reasoning as .env being gitignored for Docker.
- Vehicle type: Bruno is a general vehicle hire business, not just cars — added a VehicleType enum on Vehicle rather than modelling per-type inheritance. Business reason: all vehicle types share the same fields for this system's purposes, so a discriminator enum is simpler than a type hierarchy and still lets the fleet expand to new vehicle types by just adding an enum value. Widened to cover non-road vehicles too: Car, Suv, Van, Truck, Bus, Minibus, Motorcycle, Trailer, Tractor, Helicopter, Boat, Other.
- Removed Mileage and ServiceHistory from Vehicle: follow-up from the VehicleType change - both were car/road-vehicle-specific assumptions (odometer km, dealership-franchise servicing) that don't generalize to a helicopter or tractor, and neither is in the spec's required fields, so they were dropped rather than reworked.
- Validation error shape: ExceptionHandlingMiddleware now returns FluentValidation failures as a field-keyed errors dictionary (ValidationProblemDetails, RFC 7807 - {"errors": {"PricePerDay": ["..."]}}) instead of a flat list of message strings. Matches ASP.NET Core's own built-in model-binding error shape, so the frontend has one consistent error format and can map errors[fieldName] straight to the matching input for inline validation display.
- API key security: header-based (X-Api-Key) via ApiKeyMiddleware, checked against a key stored in User Secrets (same reasoning as the DB connection string - never hardcoded/committed). /swagger paths are excluded from the check so the docs UI itself stays browsable; actual endpoint calls (including from Swagger's "Try it out") still need the key. Swagger's Authorize button is wired up via a security definition so the key only needs to be entered once per session in the UI.
- Frontend framework: Next.js instead of the spec's literally-named React stack (Vite/CRA + React Router). Deliberate deviation, not an oversight - reasoning: Kyle's existing familiarity with Next.js/Vercel, easy Vercel deployment for this project's planned deploy step, built-in file-based routing (app/ folder structure maps directly to routes, no manual router config), and SSR/React Server Components available if useful later. Still React underneath, still TypeScript - the deviation is specifically from "Vite or CRA" + "React Router" being named explicitly in the spec's Required Stack for React.
- Package manager: pnpm instead of npm for the frontend. Reasoning: pnpm is more performant than npm - it uses a single global content-addressable store and hard-links packages into node_modules instead of copying them per-project, so installs are faster and use far less disk space, especially valuable as more packages (like shadcn/ui components) get added.
- Styling: Tailwind CSS, scaffolded in directly via create-next-app's --tailwind flag. Reasoning: Kyle's existing experience with it and convenience, not a spec requirement either way (spec doesn't name a styling approach). Also sets up for shadcn/ui later (a component library built on Tailwind) - planning to use it for the same reason as picking any component library: no point hand-building buttons/inputs/dialogs/etc from scratch when a well-built, working set already exists with little to no friction to adopt. Satisfies the spec's "basic reusable components" expectation for free rather than reinventing it.
- shadcn/ui chosen specifically because it's styled, built components and primitives ready to use out of the box - not a headless-only library requiring us to build the visual layer ourselves. Zod followed from that choice: shadcn's own documented pattern for forms (Field/FieldLabel/FieldError + React Hook Form) uses Zod as the validation/resolver layer, so Zod wasn't picked independently - it came bundled with adopting shadcn's forms approach.
- One-export-per-file convention (frontend only): every custom file (types, constants, schemas, lib helpers, hooks, components) exports exactly one thing. Applies to code we write, not shadcn's own generated components/ui/* files (those follow shadcn's own conventions and get overwritten if regenerated). Next.js route files (page.tsx/layout.tsx) are also exempt where the framework itself requires multiple exports (e.g. layout.tsx needs both `metadata` and the default component in the same file for App Router to pick them up). Services are the one deliberate exception to this rule (see next entry).
- Services grouped by entity instead of one-per-file: vehicle-service.ts (all 5 vehicle operations, mirrors VehiclesController), image-service.ts (uploadImage, mirrors ImagesController), auth-service.ts (getApiKey/setApiKey/clearApiKey, grouped the same way even though it's storage not HTTP). Reasoning: services should align with the backend API surface they call, and one-file-per-controller-equivalent reads better than one-file-per-endpoint here. Minor known wrinkle: lib/http-client.ts (the "API layer") now imports getApiKey from services/auth-service.ts (the "service layer") to attach the header - technically backwards from the lib-below-services layering described earlier, but auth-service.ts doesn't touch HTTP at all (just sessionStorage), so there's no actual circular dependency, just a label/layer crossing for a low-level cross-cutting concern.
- Removed httpClient.postForm as a separate method: it only existed because post() unconditionally JSON.stringify'd its data, which corrupts a FormData upload (stringifying FormData doesn't preserve the multipart boundary the browser needs to set). Fixed post/put with a shared serializeBody() helper that passes FormData through untouched and JSON.stringifies everything else - one post() method handles both JSON and file uploads now, no special-cased postForm needed at call sites.
- Removed VehicleType/VehicleColour type aliases (both were just `type X = number`): TypeScript is structural, so a type alias to a primitive adds zero real type safety - nothing would stop a colour value being passed where a vehicle type is expected. Vehicle/CreateVehicleRequest/UpdateVehicleRequest just use `number` directly now.
- Types/constants/schemas split into their own top-level folders (types/, constants/, schemas/), each holding one file per type/constant/schema - not bundled together like the original types/vehicle.ts. Makes it obvious where to find or add any single piece of shared shape/config.
- NotFoundException: added a plain Application-layer exception, caught in ExceptionHandlingMiddleware alongside ValidationException and mapped to 404 (ProblemDetails). Used by GetVehicleByRegistrationNumber and UpdateVehicle when the vehicle doesn't exist, instead of each handler/controller inventing its own null-check-and-return-404 pattern. Same "throw deep, catch once at the edge" approach as the validation error handling.
- Update endpoint doesn't touch ImageUrls: UpdateVehicleCommand omits ImageUrls entirely; Vehicle.Update() already defaults imageUrls to null -> keeps existing list unchanged. Deliberate scope cut for now, not an oversight - image management on update can come later.
- Edit page uses registration number, not id, as the route param: backend has no "get vehicle by id" endpoint, only by RegistrationNumber (immutable) and paginated list. Rather than add a new backend endpoint just for this, the edit page fetches by registration number and pulls the id out of the response DTO when calling updateVehicle(id, ...). Avoids unnecessary backend scope for a frontend routing convenience.
- Zod + react-hook-form + z.coerce.number() type conflict: z.coerce.number() gives the schema a mismatched input (unknown) vs output (number) type, which breaks TS generics between useForm<FormValues>, Controller's Control<T>, and zodResolver. Fixed by dropping .coerce entirely (schema fields are plain z.number()) and doing the string->number conversion explicitly in TextFormField via the input's native e.target.valueAsNumber, so RHF's actual state is always a real number, matching the schema's input type exactly.
- Reusable TextFormField / SelectFormField components: the Controller+Field+Input pattern shadcn's docs show repeats near-identically per field, and both the Create and Edit vehicle forms need the same fields - genuine reuse, not premature abstraction. Extracted once, used by both forms; this is what keeps both pages short.
- Update route/body id binding: PUT /api/vehicles/{id} takes Guid id from the route plus UpdateVehicleCommand from the body (which doesn't need to include Id at all), then the controller does `command with { Id = id }` before sending - keeps the route as the source of truth for which resource is being updated rather than trusting a body-supplied id.
- Auth storage key naming: renamed STORAGE_KEY -> API_KEY_STORAGE_KEY (moved to constants/api-key-storage-key.ts) after it read as if the actual API key value was hardcoded. It's only ever the sessionStorage slot name - the real value starts empty and is whatever the user types into the Authorize screen; nothing about the key itself is hardcoded.
- Default page size: getVehiclesPaged(pageNumber, pageSize = DEFAULT_PAGE_SIZE) now defaults pageSize to 10 at the service function itself (constants/default-page-size.ts), rather than relying on each caller (e.g. the home page) to know and pass 10 explicitly.
- Loading spinner: components/loading-spinner.tsx (lucide's Loader2Icon + animate-spin), reused across the auth gate, list loading, image upload, and form submit-button states rather than inconsistent "Loading..." text in different places.
- Edit moved from a routed page to a modal: removed app/vehicles/[registrationNumber]/edit entirely - editing now happens via a Modal triggered from the vehicle table row, reusing the Vehicle object already in hand from the paginated list (no re-fetch needed, unlike the old routed page which had to fetch by registration number). components/edit-vehicle-form.tsx holds just the form logic; the home page composes it together with VehicleView inside the shared Modal component, so the "view" and "edit" pieces stay separately reusable rather than one component doing both.
- Modal component: components/modal.tsx wraps shadcn's Dialog (open/onOpenChange/title/children), used for both the view-only modal (row click -> VehicleView) and the edit modal (Edit button -> VehicleView + EditVehicleForm stacked). Row click opens view; the Edit/Delete cell has onClick={(e) => e.stopPropagation()} so those buttons don't also trigger the row's view-modal.
- VehicleView component: image (or a placeholder icon box, same treatment as the table) plus a label/value row per field. Used identically in both the view modal and stacked above the edit form - one component, two contexts, rather than duplicating the read-only display.
- Table thumbnail column: shows vehicle.imageUrls[0] in a fixed size:10 box if present, else the same-sized muted box with a lucide ImageIcon placeholder - so the column width/layout never shifts based on whether a given vehicle has an image.
- BackButton component: components/back-button.tsx, just router.back() (next/navigation) - a plain "pop one page off the stack," not a breadcrumb/history system. Added to the New Vehicle page since it's the one remaining routed page (Edit no longer needs it now that it's a modal on the home page).
- Auth flow: an AuthProvider (React context) wraps the whole app and gates it with AuthGate - nothing renders except the Authorize screen until authorized. On mount, if a key is already in sessionStorage it's verified with a real request (getVehiclesPaged(1,1)); success -> authorized, 401 -> key cleared and the Authorize screen shows. Submitting the Authorize screen calls the same verification request with the entered key: success stores the key and unlocks the app, 401 shows "Invalid API key" and the key is cleared again, any other error rethrows (not silently treated as a bad key). The key never touches a build-time env var - it only ever lives in sessionStorage, set/read/cleared via auth-service.ts, attached by http-client.ts as the X-Api-Key header on every request from then on.
- Image upload flow: upload fires the moment a file is selected (not chained into vehicle creation on submit). Two independent actions - upload returns a URL immediately, "Add Vehicle" submit is a separate action that just sends whatever URLs already exist. Reasoning: better UX (upload failures surface immediately, not after filling the whole form), and it mirrors how the backend is already split (ImagesController and VehiclesController are unrelated endpoints; CreateVehicleCommand only ever knows about plain URL strings, never blob storage). Chaining upload->create on submit would couple two independent operations together and doesn't even remove the minor orphaned-blob risk (upload could still succeed while create fails) - it just moves the same risk later with worse UX.
- Azure Blob Storage credentials: reusing an existing POC storage account ("blobpocnexusdev"), new container "kylebruno" made for this project with anonymous read access at Blob level (not Container level - we only ever access known URLs, never need to enumerate the container, so Blob level is the better fit, not just "good enough"). Connection string + container name stored in User Secrets, same reasoning as everything else - anonymous access only covers reads, uploading always needs the connection string regardless of the container's public access setting.

Secrets / Environment Variables (what's needed if/when this gets deployed)
- ConnectionStrings:DefaultConnection - Postgres connection string. Local: User Secrets, pointing at the Docker container. Deploy: needs to point at whatever Postgres instance is hosted for production (a managed cloud Postgres, not the local Docker container) - set via the hosting platform's env vars/app settings, not committed.
- ApiKey - the header-based API key value. Local: User Secrets. Deploy: needs an equivalent secret/env var configured on the hosting platform (e.g. Azure App Service Configuration, or a secrets manager) - should probably be a different, stronger value than the local dev key.
- AzureBlobStorage:ConnectionString - Azure Storage account connection string (write access for uploads). Local: User Secrets. Deploy: same key needs to exist as a platform secret/env var; the underlying storage account itself doesn't need to change, since this container can be reused as-is.
- AzureBlobStorage:ContainerName - "kylebruno". Not sensitive on its own (just a name), but kept alongside the connection string in User Secrets for consistency. Deploy: same value, just needs to be present as config wherever it's hosted.
- Docker .env (POSTGRES_DB/USER/PASSWORD) - local-only concern for running Postgres in a container on this machine. Not relevant at deploy time since production would use a real hosted Postgres instance instead of this Docker setup.

Questions
Q: What's the dependency direction across the layers?
A: Domain depends on nothing. Application depends on Domain only. Infrastructure depends on Application (+ Domain transitively). Api depends on both Infrastructure and Application. So Domain <- Application <- Infrastructure <- Api - dependencies always point inward, toward Domain.

Q: What do Up() and Down() mean in an EF Core migration?
A: Up() applies the migration - the schema changes to move the DB forward (e.g. CreateTable). Down() reverses it - what to run to undo this migration and get back to the previous schema state (e.g. DropTable). Down() is what runs if you ever roll back a migration.

Q: The validation failure is thrown inside the MediatR pipeline behavior, not the controller - how does that error actually reach the frontend as a response?
A: Nothing in between catches it - the ValidationException just propagates up through every awaited caller (pipeline behavior -> MediatR.Send -> controller action -> MVC internals) until it hits ExceptionHandlingMiddleware, which wraps the entire rest of the pipeline in a try/catch (it's registered before MapControllers, so its "await _next(context)" covers routing + controller + MediatR + handler, all of it). That catch block is what actually sets the 400 status and writes the ValidationProblemDetails JSON to the real HTTP response. So the frontend just gets a normal HTTP 400 + JSON body like any other error - nothing special on its end.

Q: How does Moq work briefly?
A: Moq generates a fake in-memory implementation of an interface at runtime (no real DB/HTTP/etc behind it). new Mock<IVehicleRepository>() creates the fake; .Object is the actual instance passed into the handler's constructor same as DI would. .Setup(...) configures what a specific method call should return (anything not set up just returns a harmless default, doesn't throw). .Verify(...) asserts after the fact that a method was actually called, how many times, with what args - e.g. confirming AddAsync was called once. This only works because IVehicleRepository is an interface - Moq can't fake a concrete class's non-virtual members, which is part of why the repository is designed as an interface in the first place.

Q: In theory, how would we add a new field via a migration, and do we need to manually chase down every place that references the old shape?
A: 1) add the property to Vehicle (Domain), 2) update VehicleConfiguration if it needs specific mapping (Infrastructure), 3) "dotnet ef migrations add <Name>" - EF diffs against ApplicationDbContextModelSnapshot.cs and generates Up()/Down(), 4) "dotnet ef database update" to apply it.
On due diligence: mostly yes, but the compiler does the heavy lifting. Since Vehicle's constructor and Update() take explicit params (not public setters), adding a required param breaks every existing call site (CreateVehicleCommandHandler, UpdateVehicleCommandHandler, unit tests constructing a Vehicle) at compile time until fixed - can't silently forget one. Still need to manually add it to the relevant Command(s), a validator rule if needed, VehicleDto + MappingExtensions.ToModel(), and eventually the frontend.

Q: Why did the font look wrong/default even though Geist was set up?
A: Real bug - globals.css's @theme inline block expects a CSS variable literally named --font-sans, but layout.tsx's Geist() call only ever defined --font-geist-sans (mismatched name). Since --font-sans was never actually set, Tailwind's font-sans utility fell back to the default system font stack the whole time - Geist was never actually applied. Fixed by naming the Geist variable --font-sans directly (`Geist({ variable: "--font-sans", ... })`) so it matches what globals.css looks for.

Q: What's the difference between PUT and PATCH?
A: PUT means "replace the whole resource with this representation" - the client sends the full set of editable fields, and anything omitted is implicitly cleared/reset. It's idempotent (sending the same PUT twice leaves the resource in the same state). PATCH means "apply a partial update" - the client sends only the fields that should change, everything else on the resource stays untouched. This is why UpdateVehicleCommand is a PUT: it requires every editable field (VehicleType, Make, Model, Year, Colour, SellerName, PricePerDay) every time, matching PUT's full-replacement semantics. If we ever wanted to let the frontend update just one field (e.g. only PricePerDay) without resending everything else, PATCH would be the more correct verb - but that needs a partial-update DTO/handler designed for it, not just swapping the HTTP method.

Q: What is Swashbuckle?
A: .NET library that auto-generates OpenAPI/Swagger docs from controllers/DTOs and serves the Swagger UI page. Satisfies the spec's "Swagger documentation enabled" requirement.

Q: How does VehicleRepository know it's talking to Postgres instead of Mongo etc, and how does it get the DbContext - is that passed in by the handler?
A: VehicleRepository itself doesn't know it's Postgres - it only knows ApplicationDbContext, and EF Core's LINQ API (_dbContext.Vehicles.FirstOrDefaultAsync(...) etc) is provider-agnostic. The one place Postgres gets chosen is Program.cs: builder.Services.AddDbContext<ApplicationDbContext>(options => options.UseNpgsql(...)) - that .UseNpgsql(...) line is the single point in the whole solution that says "this DbContext talks to Postgres." If swapping to a different relational DB (e.g. SQL Server), that's the only line that would need to change (Mongo is a bigger swap since it isn't relational and EF Core doesn't support it the same way).

On how the DbContext gets into the repository - not through the handler, and nothing is passed manually anywhere. It's constructor injection via .NET's built-in DI container:
1. Program.cs registers two things: ApplicationDbContext (via AddDbContext) and IVehicleRepository -> VehicleRepository (via AddScoped).
2. When a request comes in, MediatR asks the DI container for a CreateVehicleCommandHandler. Its constructor needs an IVehicleRepository - the container sees that's registered to resolve to VehicleRepository.
3. To build a VehicleRepository, the container looks at its constructor, sees it needs an ApplicationDbContext, and supplies one automatically - because that's also registered.
4. So: Api (DI container assembles everything) -> Handler only ever sees IVehicleRepository -> VehicleRepository only ever sees ApplicationDbContext -> ApplicationDbContext is the only thing that knows about Npgsql/Postgres.

Nobody manually passes ApplicationDbContext anywhere - the container wires the whole chain based purely on constructor parameter types and what's registered in Program.cs. This is also why the handler can be unit tested by just mocking IVehicleRepository - it never needs a real database at all.

Technical Details

Azure Blob Storage (vehicle images)
- Reusing an existing Azure resource from a prior POC rather than provisioning new: Storage account "blobpocnexusdev", new blob container "kylebruno" created specifically for this project, container anonymous access level set to "Blob" (anonymous read access to individual blobs by URL, not container listing).
- Because the container allows anonymous blob-level read, no SAS token or auth is needed for retrieval - once a file is uploaded, its blob URL is directly publicly viewable. This is what satisfies "image retrieval from url" simply: the DB just needs to store the URL, no dedicated retrieval endpoint required.
- Upload still goes through the backend (not client-direct-to-blob) so the backend controls what gets stored and appends the resulting URL to Vehicle.ImageUrls.

EF Core persistence setup
- Infrastructure/Persistence/ApplicationDbContext.cs — DbSet<Vehicle>, applies entity configs from the assembly (ApplyConfigurationsFromAssembly) so new entity configs get picked up automatically without editing OnModelCreating each time.
- Infrastructure/Persistence/Configurations/VehicleConfiguration.cs (IEntityTypeConfiguration<Vehicle>) — table name "Vehicles", unique index on RegistrationNumber, max lengths on string fields (RegistrationNumber 20, Make/Model 50, SellerName 100), PricePerDay mapped as numeric(10,2) (never float/double for money), Colour/ServiceHistory enums stored as int.
- Soft delete enforced via a global query filter on the entity config (HasQueryFilter(v => !v.IsDeleted), in VehicleConfiguration.Configure) rather than each handler/query remembering to filter it out — every query against Vehicles automatically excludes soft-deleted rows at the EF Core level, applied by EF itself as a silent WHERE clause on every LINQ query against DbSet<Vehicle>. Confirmed in practice: GetByIdAsync/GetByRegistrationNumberAsync/GetPagedAsync all just write plain queries with zero IsDeleted-awareness and still exclude soft-deleted rows correctly - including SoftDeleteVehicle's own repeat-delete case (can't fetch an already-deleted vehicle to delete it again, so it 404s).
- Program.cs registers ApplicationDbContext via AddDbContext with UseNpgsql, reading the connection string from configuration (ConnectionStrings:DefaultConnection) — supplied via .NET User Secrets locally (see commands below), never hardcoded or committed.

Code-first migrations — flow
- Code-first means the C# entity + EF Core config is the source of truth for the schema, not a hand-written SQL script. Flow: 1) define/change Vehicle entity (Domain) 2) configure it via VehicleConfiguration (Infrastructure) 3) run "dotnet ef migrations add <Name>" - EF diffs the model against the last snapshot and generates a migration file with Up()/Down() 4) run "dotnet ef database update" - applies pending migrations to the actual DB.
- Requires Microsoft.EntityFrameworkCore.Design in both the project holding the DbContext (Infrastructure) and the startup project (Api) - the CLI tools need it in the startup project to build/run the app's DI container.
- Each migration produces 3 files: <timestamp>_<Name>.cs (the actual Up/Down), <timestamp>_<Name>.Designer.cs (tooling metadata), and ApplicationDbContextModelSnapshot.cs (single file, current full model state, updated every migration so EF can diff future changes against it). All 3 get committed to git.
- First migration: InitialCreate - creates the Vehicles table matching VehicleConfiguration (unique index on RegistrationNumber, numeric(10,2) PricePerDay, enums as int, etc.).

CORS
- Added a named CORS policy allowing http://localhost:3000 (Next.js dev server default port), AllowAnyHeader + AllowAnyMethod, registered via AddCors/UseCors in Program.cs.
- Ordering matters: UseCors is placed BEFORE ApiKeyMiddleware in the pipeline. Browser CORS preflight (OPTIONS) requests never include custom headers like X-Api-Key, so if ApiKeyMiddleware ran first it would reject every preflight with 401 and break CORS entirely. ASP.NET's CORS middleware short-circuits matching preflight requests itself (responds directly, never calls next), so placing it first means preflights never reach the API key check at all.

Swagger wiring
- Replaced the template's built-in AddOpenApi()/MapOpenApi() (just a raw OpenAPI JSON document, no browsable UI) with Swashbuckle: AddEndpointsApiExplorer() + AddSwaggerGen() in services, UseSwagger() + UseSwaggerUI() in the dev-only pipeline block. This is what actually gives a visual Swagger page at /swagger, satisfying the spec's "Swagger documentation enabled" requirement.
- Wiring Program.cs alone isn't enough to actually see the UI when running from Visual Studio - Properties/launchSettings.json also needs "launchBrowser": true and "launchUrl": "swagger" on each profile (http/https), otherwise the app runs fine but no browser opens (or it opens to a blank/404 root page with no launchUrl set).

Unit tests
- BrunoVehicleHire.Application.Tests (xUnit + Moq), references Application only - mocks IVehicleRepository, no real DB/EF Core involved, proving the "handler can be unit tested without a real database" point from earlier. CreateVehicleCommandHandlerTests (1 test) + GetVehicleByRegistrationNumberQueryHandlerTests (2 tests: found, not-found -> NotFoundException).

Frontend architecture
- Folder layout: app/ (Next.js routes), components/ (shadcn primitives in ui/, custom components elsewhere), lib/ (http-client.ts + api-error.ts - the "API layer" - plus auth-storage/), services/vehicles/ (one function per file, calls http-client - the "service layer"), types/, constants/, schemas/ (one type/constant/schema per file), contexts/ + hooks/ (auth context/hook). Mirrors the spec's named "UI components / API-service layer / Models-DTOs" split, with the API/service layer further divided into transport vs use-case orchestration for clarity (not a strict backend-style Clean Architecture port - there's no swappable-infrastructure need on the frontend, just a good separation of concerns).
- API key handling: NOT baked in as a NEXT_PUBLIC_ build-time env var (that would ship it inside the browser bundle, visible to anyone). Instead: an Authorize screen captures the key at runtime, verifies it with a real API call, and holds it client-side (session storage) for the rest of the session, attached to every subsequent request. Base API URL is still a NEXT_PUBLIC_ env var since it isn't sensitive - satisfies "environment-based API config."
- shadcn/ui version gotcha: this project's shadcn CLI (v4.18+) is a notably newer/restructured version than what's commonly documented - uses @base-ui/react instead of Radix directly, a "base-nova" style/preset system, and no longer has a single generated "Form" component. Forms are composed manually from a "Field" primitive (Field/FieldLabel/FieldError) + React Hook Form + Zod + @hookform/resolvers, installed via `shadcn add field` (not `add form`).
